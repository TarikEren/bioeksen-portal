Two colours, and what they will and won't do

The whole system derives from the logo. Sampled from the mark itself, the brand is exactly two values — everything else is a tone of one of them, or is reserved for a problem.

The constraint

The brand green cannot carry a white label

This is the finding that shapes every other decision, so it comes first. At 3.49:1 against white, the logo green sits below the 4.5:1 that normal-size text needs — in either direction. It is a graphic colour, not a text colour.

So the brand green stays exactly as drawn wherever it behaves as a graphic — the mark, the area rule, an icon, a border. Where it has to hold a label, it darkens by 8% and keeps its hue. Nobody reading the screen perceives two greens; the contrast checker perceives the difference, which is the point.

Decisions

Four calls, and why

01

Success is not a colour

In e-IFU, finding the document is the ordinary outcome — it happens thousands of times for every failure. A green banner announcing it trains people to ignore green, which is exactly the colour the failure state needs them not to ignore. Success is presented as content: the document appears. Strong colour is spent only on problems.

02

One green family, no separate success hue

Because e-IFU does not colour its success case, nothing competes with the brand green. It can be identity, primary action, and Academy's positive state at once — progress bars, completed lessons, a valid certificate. A second green would have been two greens nobody could tell apart.

03

Dark mode is wired, not built

Every colour is a semantic token today, and no component holds a literal. The dark blocks exist and are deliberately empty. Turning it on later means filling them in — not touching a single component.

04

The two areas differ by one token

e-IFU and Academy share every component, every type scale, every spacing step. The only difference is the rule under the header — green for e-IFU, grey for Academy. Enough to know where you are; not enough to be two products.

In context

Clinical and precise

Small radii, hairlines instead of shadows, generous white space, and identifiers always set in mono — a catalog or LOT number is compared character by character, so it never sits in the sans face. IBM Plex throughout: drawn for technical contexts, with a true monospace companion.

Rules

What the checker enforces

scripts/check_design_tokens.py runs in make check and fails the build on a contrast regression, so these are not conventions to remember.

CONTRAST

Body text meets 4.5:1; large text and meaningful UI boundaries meet 3:1. --color-text-muted at 4.9:1 is the lightest text permitted anywhere — there is no lighter tier.

NEVER ALONE

Colour never carries meaning by itself. Every state pairs colour with an icon and a text label, and every error carries its registered code from error-codes.md.

MONO

Catalog numbers, LOT numbers, revisions, dates, hashes and percentages are always monospace. They are compared character by character; the sans face makes that harder.

FOCUS

The focus ring is never removed. If a design needs a different one, it is replaced by one meeting 3:1 against its background.

NO LITERALS

No component contains a hex value. Primitives like --green-600 are for the token layer only; components reference semantic tokens.

TURKISH

Every string here is illustrative. Real UI text comes from translation keys in both tr and en — and Turkish runs longer, so layouts are tested at the longer string.
