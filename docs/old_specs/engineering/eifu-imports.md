# e-IFU and LOT Import Rules

## Supported formats

Support CSV and XLSX for Catalog Number and LOT bulk operations where appropriate.

## Catalog Number import

Catalog Number belongs to one Product. Reject duplicate Catalog Number identity unless the operation is an explicitly reviewed correction.

Pack size may be stored as business metadata.

## LOT import

Expected minimum concepts:

- Catalog Number
- LOT Number
- manufacturing date, either explicitly supplied by approved input or parsed under the documented Bioeksen LOT rule

LOT imports may occur daily.

### How it is run

`POST /api/v1/catalog/lot-imports/preview`, then `POST /api/v1/catalog/lot-imports`
(`catalog.lot.manage`). Both take the same input and **preview writes nothing**.
Commit plans every row again inside its transaction -- the table may have
changed since the preview -- and writes only what that plan says is new.

The input is **pasted text** (what a copy from Excel produces: tab-separated;
semicolon or comma CSV also read) or a **file**: `.xlsx` (first sheet), `.csv`,
`.tsv`, `.txt`, at most 5 MB. A CSV that is not valid UTF-8 is read as
Windows-1254, which is what Excel writes on a Turkish system. At most 5,000 data
rows per import (`IMPORT_ROW_LIMIT_EXCEEDED`).

Two scopes:

- **Everything at once** (the LOT import screen). Every row names its catalog
  number; the product each LOT will belong to is shown, grouped, in the preview.
- **One product** (from the product's page, `product_id`). Rows naming another
  product's catalog number are `INVALID_CATALOG_NUMBER`. A catalog number may be
  chosen (`catalog_number_id`) for rows that name none, so a list of LOTs can be
  pasted as a single column.

### The template

The import screen offers a blank workbook, `/templates/lot-import-template.xlsx`,
generated by `scripts/generate_lot_import_template.py` from the locale files.
Its first sheet is the header row alone, with the catalog number and LOT
columns formatted as **text** -- a spreadsheet left to guess turns a LOT into a
number or drops a leading zero, and a LOT changed on the way in never resolves.
The second sheet holds the instructions and is never read. Sent back unfilled
it is `IMPORT_NO_ROWS`.

### Columns

A header row is recognised by its labels, in either language, ignoring case and
accents: `Katalog No` / `Catalog No` / `catalog_number`, `LOT` / `LOT No` /
`lot_number`, `Üretim Tarihi` / `Manufacturing date` / `manufacturing_date`.
Other columns are ignored. Header labels are normalised because they are labels;
the values under them never are.

Without a header the columns are positional: one column is the LOT (a catalog
number must be chosen), two are catalog number and LOT, three are catalog
number, LOT and manufacturing date. A missing column is
`IMPORT_COLUMNS_MISSING`, naming it in `details`.

The manufacturing date column is optional. `YYYY-MM-DD`, `DD.MM.YYYY` or
`DD/MM/YYYY`, or a date cell in an XLSX -- day first, never month first.

### Row reasons

Every row gets an outcome and one reason code, stored in
`ImportRowResult.message` and translated by the screen:

| Outcome | Reason | When |
|---|---|---|
| `CREATED` | (none) | New, and consistent with everything it can be checked against. |
| `ALREADY_EXISTS` | `LOT_ALREADY_EXISTS` | Registered under this catalog number with the same date. |
| `ALREADY_EXISTS` | `IMPORT_DUPLICATE_ROW` | An earlier row in the same source names the same catalog number and LOT. |
| `CONFLICT_REVIEW_REQUIRED` | `LOT_CONFLICT_REVIEW_REQUIRED` | Registered under this catalog number with a different date. |
| `CONFLICT_REVIEW_REQUIRED` | `EIFU_LOT_DATE_CONFLICT` | The supplied date disagrees with the one the LOT encodes. |
| `CONFLICT_REVIEW_REQUIRED` | `LOT_KIT_CODE_MISMATCH` | The LOT does not end with the kit code its catalog number implies (ADR-0013). A catalog number with no format is not checked: its final letter is unknown. |
| `CONFLICT_REVIEW_REQUIRED` | `IMPORT_CONFLICTING_ROWS` | Another row in the same source names this catalog number and LOT and disagrees -- a conflicting or unreadable supplied date. None of them is written: writing the clean one would let the encoded date win by the accident of a second row (ADR-0008). |
| `INVALID_CATALOG_NUMBER` | `EIFU_CATALOG_NUMBER_NOT_FOUND` | No catalog number matches exactly. |
| `INVALID_CATALOG_NUMBER` | `CATALOG_NUMBER_BELONGS_TO_OTHER_PRODUCT` | Scoped to a product, and this catalog number is another's. |
| `INVALID_LOT_FORMAT` | `IMPORT_LOT_MISSING` | The LOT cell is blank. |
| `INVALID_LOT_FORMAT` | `EIFU_LOT_FORMAT_INVALID` | Not `B` + `YYMMDD` + more (ADR-0008). |
| `INVALID_DATE` | `EIFU_LOT_DATE_INVALID` | The encoded date is not a calendar date. |
| `INVALID_DATE` | `IMPORT_SUPPLIED_DATE_INVALID` | The supplied date cannot be read, or is not a calendar date. |

**Nothing but `CREATED` is written.** A conflict is not registered with a flag
here: it reaches a person, who registers that one LOT deliberately from the
product page, where a supplied date that disagrees is stored with
`has_date_conflict` set and refused by resolution until corrected.

## Bioeksen LOT date parsing

Current documented pattern:

`BYYMMDD...`

Example:

`B2603091224GHPVV`

- Prefix: `B`
- Date segment: `260309`
- `YY=26`, `MM=03`, `DD=09`
- manufacturing date: `2026-03-09`

### Transport cleanup versus semantic normalization

These are different things and only one of them is permitted.

**Transport cleanup — allowed.** Artefacts of how the value travelled, not of what
the value is. Spreadsheet cells routinely carry these:

- surrounding whitespace, including tabs and non-breaking spaces
- a UTF-8 BOM on the first cell of a file
- surrounding quote characters added by a CSV exporter

```
raw cell        " B2603091224GHPVV "
canonical input "B2603091224GHPVV"     <- stored as lot_number
```

Store the cleaned value as `lot_number` and retain the raw cell in
`ImportRowResult.raw_row`, so the original is never lost.

**Semantic normalization — forbidden** unless a documented Bioeksen rule
specifically permits it:

- no case conversion; `b2603091224ghpvv` is **not** silently promoted to
  `B2603091224GHPVV`, it fails as `EIFU_LOT_FORMAT_INVALID`
- no hyphen, dot or separator removal
- no internal whitespace rewriting
- no zero-padding, truncation or character substitution

The distinction is which question you are answering. Removing a leading space
answers "what did the file actually contain". Upper-casing answers "what did they
probably mean" — and guessing intent about the identifier that selects a
regulatory document is not the import layer's job.

Implementation guidance:

- Apply transport cleanup once, at the import boundary, before validation.
- Parse using a dedicated tested function, not substring logic scattered through views/import code.
- Validate real calendar dates.
- The LOT ends with a kit code — `Product.kit_code_base` plus a letter fixed by
  `CatalogNumber.format` (vCAP `V`, lyophilized `L`, liquid none). It is checked
  by suffix match, never parsed out — a base ending in `V` and a vCAP marker
  are indistinguishable from outside. See ADR-0013.
- A LOT whose kit code disagrees with the product its catalog number resolves to
  is `CONFLICT_REVIEW_REQUIRED`, and nothing is written. A product with no
  recorded base is simply unchecked. (The single-LOT form reports a mismatch
  and registers the LOT: a person typing one LOT is the review.)
- Assume nothing else about the remainder of the LOT.
- If an explicit approved manufacturing date is supplied and differs from the encoded date, flag a conflict for authorized review; do not silently prefer one.

## Duplicate behavior

Do not silently upsert conflicting LOT data.

Recommended behavior:

- exact duplicate: skip with warning/status `ALREADY_EXISTS`;
- duplicate with changed data: `CONFLICT_REVIEW_REQUIRED`;
- authorized correction: explicit action with audit event.

## Import report

Return counts and row-level outcomes such as:

- created
- skipped duplicate
- invalid Catalog Number
- invalid LOT format/date
- conflict
- failed

Importing must not partially hide failures.

Import batch and row-result fields are defined in `data-model-fields.md`. Row
reasons are the table above; where one names a condition that also exists as an
API error, it uses that error's code.

A commit that fails after it started is recorded as a `FAILED` batch with its
`failure_code`, outside the transaction that rolled back, so an attempt that
wrote nothing is still on the record. The batch's audit event is
`catalog.lot_import.completed`; each LOT it created carries `import_batch`.
